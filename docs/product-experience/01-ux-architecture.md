## 1. الغرض من هذه الوثيقة

تحدّد هذه الوثيقة **عمارة تجربة المستخدم (UX Architecture)** لمنصة ABC كأساس دائم يبنى عليه تطوير الواجهات، وليس كبروتوتايب مؤقت. تعمل كطبقة Product فوق طبقات الـ Domains المعتمدة في Capability Map، وتضمن أن كل شاشة تُبنى لاحقاً تخدم تدفقاً محدداً وقراراً معمارياً موثقاً.

مبادئ التنسيق مع Architecture Team:
- كل تدفق في هذه الوثيقة يستند إلى Domain موجود أو مخطط في capability-map.md.
- لا تصميم لأي شاشة تعتمد على بيانات غير موجودة في الـ Prisma Schema المعتمد.
- أي شاشة تُضاف لاحقاً خارج خريطة الشاشات (Screen Map) تمر عبر مراجعة الـ Frontend Architecture Group.

## 2. مبادئ تجربة المنتج (Product UX Principles)

| # | المبدأ | التطبيق العملي |
|---|--------|----------------|
| 1 | **الثقة قبل السرعة** | إظهار حالة التحقق (Verification Level) بشكل دائم: `UNVERIFIED → BASIC → VERIFIED → TRUSTED → FLAGSHIP` (ADR-018). الشارة (Badge) في كل بطاقة مورد ومنتج. |
| 2 | **المؤسسة هي الهوية** | في بوابات الأعمال، الكيان الأول هو الـ Organization وليس المستخدم (ADR-018). الواجهة تعكس ذلك: اسم المؤسسة، شعارها، أدوارها المتعددة. |
| 3 | **البيانات المعقدة تُبسّط** | الـ BOQ وقوائم الكميات والمواصفات تُعرض كجداول قابلة للفرز/التصدير، مع ملخص رقمي واضح (مجموع كميات، إجمالي تقديري) — لا ككتل نصية. |
| 4 | **دورة حياة العملية مرئية** | كل كيان له حالة (State Machine): RFQ، عروض، PO، فاتورة. يعرض النظام الخطوة الحالية والخطوات التالية (Stepper) بدل تركه للمستخدم للتخمين. |
| 5 | **Trilingual: RTL-First (AR/UR) + English-Ready** | **متطلب رسمي معتمد:** المنصة تدعم 3 لغات — **العربية (RTL)** أساسية، **الإنجليزية (LTR)** واجهة كاملة معكوسة، **الأردية (RTL)** واجهة كاملة. كلاهما RTL، والإنجليزية LTR. هذا أساس Sprint 1 Implementation وليس خياراً لاحقاً. |
| 6 | **Mobile-First للعاملين في الموقع** | المهندسون والعمال وسائقو التوصيل يعملون من الجوال على المواقع. التجربة الجوالية أولوية وليست نسخة مصغرة. |
| 7 | **Zero-Retraining إدخال** | نماذج تُملأ مرة واحدة تُعاد استخدامها (عناوين، ضريبة، بنوك، مؤسسات). |
| 8 | **إشعارات قابلة للتنفيذ** | كل إشعار يتضمن إجراء (CTA): "لديك عرض جديد ← مراجعة العرض"، وليس نصاً فقط. |
| 9 | **أوضاع فارغة مدروسة** | كل قائمة فارغة تشرح "لماذا" وتقترح الخطوة التالية، خصوصاً في البوابات بعد التسجيل مباشرة. |
| 10 | **إمكانية الوصول (A11y)** | WCAG 2.1 AA، تباين ألوان، تنقل بلوحة المفاتيح، تسميات ARIA — كمعيار قبول وليس تحسيناً لاحقاً. |

## 3. الجمهور والشخصيات (Audience & Personas)

### الأدوار (من ABC_PLATFORM_ARCHITECTURE_v1 + ADR-018)

| الرمز | الدور | البوابة | الاحتياج المركزي |
|---|---|---|---|
| `OWNER` | مالك مشروع | بوابة المالك | طرح مشروع، توظيف مقاول/استشاري، متابعة التنفيذ |
| `CONSULTANT` | مهندس/استشاري | بوابة الاستشاري | الإشراف، المواصفات، قبول الأعمال، شهادات |
| `CONTRACTOR` | مقاول | بوابة المقاول | البحث عن مشاريع، تقديم عروض، شراء مواد، إدارة عمالة |
| `SUBCONTRACTOR` | مقاول فرعي | بوابة المقاول | التخصصات (كهرباء، تشطيبات) |
| `WORKSHOP` | ورشة | بوابة المورد/المصنع | عرض منتجات مصنّعة محلياً |
| `FREELANCER` | مستقل | بوابة القوى العاملة | فرص عمل، ملف مهارات، تدريب |
| `SUPPLIER` | مورد | بوابة المورد | كتالوج، مخزون، عروض أسعار، طلبات |
| `TRADER` | تاجر | بوابة المورد | أسعار تنافسية، مخزون سريع |
| `ADMIN` | إداري | بوابة الإدارة | إشراف، تحقق، تحليلات، محتوى |

> ملاحظة: المنصة تتبنى نموذج **Organizations ذات أدوار متعددة** (ADR-018). أي مؤسسة يمكن أن تحمل أكثر من دور (مصنع + مورد + تاجر). البوابة تظهر حسب الأدوار المفعّلة للمؤسسة، مع إمكانية تبديل سياق الدور من نفس الشاشة.

### الشخصيات المرجعية (Design Personas)

| الشخصية | التفاصيل | سيناريو رئيسي |
|---|---|---|
| **م. خالد — مدير مشتريات في مقاولة كبرى** | مقاول عام، يتعامل مع 40+ مورداً، يشتري مواد شهرياً بعقود | رفع BOQ لمشروع → توليد RFQs → مقارنة العروض → ترسية → تتبع التوريد |
| **أ. سارة — مورد مواد بناء** | تاجر جملة، لديها مخزون فعلي، تريد عرضاً رقمياً يلغي المكالمات | بناء ملف المؤسسة → رفع الكتالوج والمخزون → استلام RFQ → تقديم عرض → فاتورة |
| **م. عمر — مهندس موقع في شركة استشارية** | يستخدم الجوال في الموقع، يحرر تقارير فحص | فتح مشروع تحت الإشراف → فحص مواد → NCR → شهادة قبول |
| **أ. أحمد — عامل بارع (حدادة)** | مهارات عملية، سيرته ليست رقمية | إنشاء ملف مهارات (صور أعمال) → التقدم لوظائف → دورة تدريبية → شهادة |
| **فريق الإدارة في ABC** | مشرفون على المنصة | لوحة تحكم موحدة: تحقق، تنبيهات، نمو، مواضيع دعم |

## 4. هيكل المعلومات (Information Architecture)

### 4.1 البنية العامة

```
ABC — هيكل المعلومات
│
├── عام (Public)
│   ├── الصفحة الرئيسية (Landing)
│   ├── السوق (منتجات، موردون) — تصفح بدون تسجيل
│   ├── الوظائف (تصفح)
│   ├── التدريب (تصفح الدورات)
│   └── المناقصات العامة
│
├── الحساب (Account)
│   ├── تسجيل دخول / إنشاء حساب
│   ├── الملف الشخصي (User Profile)
│   └── الإعدادات (MFA، كلمة مرور، لغة)
│
├── المؤسسة (Organization Center)
│   ├── ملف المؤسسة والأدوار
│   ├── الأعضاء والأدوار (RBAC)
│   └── التحقق KYC/KYB + الوثائق
│
├── بوابات الدور (Role Workspaces) — السمة الأساسية
│   ├── لوحة المورد Supplier Portal
│   ├── لوحة المصنع Manufacturer Portal
│   ├── لوحة المقاول Contractor Portal
│   ├── لوحة الاستشاري Consultant Portal
│   ├── لوحة القوى العاملة Workforce Portal
│   ├── لوحة مزوّد التدريب Training Provider Portal
│   └── لوحة الإدارة Admin Portal
│
└── وحدات عرضية (Cross-cutting) — تظهر داخل أي بوابة حسب الصلاحية
    ├── المشتريات Procurement (RFQ → PO → Delivery → Invoice)
    ├── السوق Marketplace
    ├── الجودة Quality
    └── الإشعارات والتقارير
```

### 4.2 مبدأ "بوابة لكل دور، وحدة مشتركة للبيانات"

- **بوابات (Workspaces):** مساحات تنقل أفقية مرتبة حسب دور المستخدم، تمنح الأولوية لمهام الدور.
- **وحدات (Modules):** مساحات بيانات مشتركة تُضاف للبوابة وفق الصلاحيات (مثل وحدة المشتريات داخل بوابة المقاول والمورد).
- **القاعدة:** لا يُخفى المفهوم، يُعاد ترتيبه. المقاول والمورد يريان نفس "دورة المشتريات" لكن من زاويتيهما.

## 5. تدفقات المستخدم (User Flows)

> اصطلاح: `[شاشة]` = وجهة، `{حدث}` = فعل مستخدم/نظام، `→` = انتقال. خطوط الحالة `(State)` تشير إلى الـ State Machines المعتمدة.

### 5.1 التدفق العام — Onboarding

```
[Landing] → {اختيار نوع الحساب}
  ├── فردي (FREELANCER / عامل) → [إنشاء حساب] → [الملف الشخصي] → [ملف المهارات] → ✅
  ├── مؤسسة (مقاول/مورد/مصنع/استشاري/تدريب) → [إنشاء حساب] → [إنشاء مؤسسة] →
  │     → [إضافة أدوار المؤسسة] → [دعوة الأعضاء] → [KYC/KYB] → ✅
  └── مالك مشروع → [إنشاء حساب] → [ملف المالك] → [مشروع جديد] → ✅

قاعدة: لا يمكن نشر أي محتوى تجاري (منتج/عرض/وظيفة) قبل إتمام الحد الأدنى من التحقق.
```

### 5.2 بوابة المقاول — Contractor Portal

```
[لوحة المقاول]
  ├── المشاريع (Projects)
  │     [قائمة مشاريعي] → [مشروع جديد] → {بيانات المشروع} →
  │     [تفاصيل المشروع] → [تحميل BOQ] → {رفع Excel/CSV أو إدخال يدوي}
  │        → [معاينة الكميات] → {تحقق من الأصناف والوحدات} → [إرسال للاستشاري/الموافقة]
  │     حالة المشروع: PLANNING → IN_PROGRESS → COMPLETED | ON_HOLD
  │
  ├── المناقصات (Tenders)
  │     [قائمة مناقصات متاحة] → [تفاصيل مناقصة] → [تقديم عرض] → {مبلغ/مدة/مستندات}
  │     → [قائمة عروضي] → حالة: PENDING → ACCEPTED | REJECTED | WITHDRAWN
  │
  ├── طلبات الشراء (RFQs)
  │     [طلبات الشراء] ← (من BOQ تلقائياً أو يدوياً)
  │     [إنشاء RFQ] → {أصناف/كميات/موعد تسليم} → [إرسال لموردين مقترحين]
  │        → [قائمة العروض الواردة] → [مقارنة العروض] → {ترسية} → [أمر شراء PO]
  │
  ├── الموردون المفضلون
  │     [قائمة موردين] → [ملف مورد] → {حفظ كمورد مفضل / إنشاء علاقة} → [مفاوضة/عقد]
  │
  └── الفريق والعمالة
        [إدارة فريق] → [دعوة أعضاء] → [أدوار داخل المؤسسة] → [ربط وظائف بالمشروع]
```

**سيناريو حرج (Happy Path):** م. خالد يستلم عقد مشروع → يرفع BOQ → النظام يقترح أصنافاً مطابقة للكتالوج → يرسل RFQ تلقائياً لأربعة موردين → يقارن العروض (سعر/مدة/تقييم/تحقق) → يرسي على الأفضل → ينشأ PO → تتبع التوريد → فحص الجودة → فاتورة → دفع → تقييم.

### 5.3 بوابة المورد — Supplier Portal

```
[لوحة المورد]
  ├── الملف التجاري (Company Profile)
  │     [ملف المؤسسة] → [بيانات عامة] → [الفروع] → [مناطق التغطية]
  │     → [التحقق KYC] → مستوى: UNVERIFIED → BASIC → VERIFIED → TRUSTED → FLAGSHIP
  │     → [الشهادات والرخص] → [البيانات البنكية] → [القدرات (Capabilities)]
  │
  ├── المنتجات (Products)
  │     [قائمة المنتجات] → [إضافة منتج] → {إما منتج رئيسي من المصنع أو عرض لمنتج موجود}
  │     → [تفاصيل المنتج] → [إدارة العروض السعرية لكل منتج]
  │
  ├── المخزون (Inventory)
  │     [المستودعات] → [إضافة مستودع] → [الأصناف: كميات فيزيائية/محجوزة/متاحة]
  │     → [استيراد Excel] → [سجل الحركات] → [تنبيهات انخفاض المخزون]
  │
  ├── العروض السعرية (Offers / RFQ)
  │     [قائمة RFQ واردة] → [تفاصيل RFQ] → [تقديم عرض سعر] → {سعر، مدة تسليم، شروط}
  │     → حالة العرض: PENDING → ACCEPTED → REJECTED | WITHDRAWN
  │
  ├── الطلبات (Orders)
  │     [أوامر الشراء] → [تأكيد] → [شحن/تسليم] → [إصدار فاتورة] → [دفع] → [تقييم]
  │
  └── التحليلات (Analytics)
        [المؤشرات] → (تُحسب تلقائياً من البيانات، ADR-018):
        إجمالي الطلبات · نسبة الإنجاز · نسبة التوريد في الوقت · متوسط التقييم ·
        معدل الفوز بالعروض · متوسط زمن الاستجابة للـ RFQ
```

### 5.4 بوابة المصنع — Manufacturer Portal

```
[لوحة المصنع]
  ├── المنتجات الرئيسية (Product Masters)
  │     [قائمة المنتجات] → [منتج جديد] → {SKU، مواصفات، وحدات، صور}
  │     → [أوراق البيانات الفنية TDS] → [أوراق السلامة SDS]
  │     حالة: DRAFT → PUBLISHED → ARCHIVED (ADR-019)
  │
  ├── العلامات التجارية (Brands)
  │     [إدارة العلامات] → [إسناد منتجات لعلامة]
  │
  ├── الموردون المعتمدون
  │     [قائمة موردين يعرضون منتجاتي] → [تفويض توزيع] → {isAuthorized + وثيقة تفويض}
  │
  └── أسواق المنتج
        [أين يُباع منتجي] → [الأسعار في السوق] → [مؤشرات العرض والطلب]
```

**مبدأ رئيسي:** المصنع يملك `ProductMaster`، والموردون يملكون `SupplierProductOffering` (ADR-019). المصنع لا يبيع مباشرة عبر الواجهة في هذا السبرينت، بل يغذي السوق عبر شبكة موزعينه.

### 5.5 بوابة المهندس / الاستشاري — Consultant Portal

```
[لوحة الاستشاري]
  ├── المشاريع تحت الإشراف
  │     [قائمة مشاريع] → [تفاصيل] → [المواصفات والرسومات] → [BOQ معتمد]
  │
  ├── الموافقات
  │     [قائمة موافقات معلقة] → [تفاصيل مستند] → {اعتماد / طلب تعديل}
  │
  ├── فحص الجودة (Quality)
  │     [فحوصات معلقة] → [إنشاء فحص] → {مواد/عينات/نتائج PASS|FAIL|N_A}
  │     → [إرفاق صور] → [NCR عند الخلل] → [تقرير فحص]
  │
  ├── شهادات القبول
  │     [قائمة شهادات] → [إنشاء شهادة قبول] → [اعتماد نهائي]
  │
  └── التوصيات الفنية
        [مكتبة المواصفات] → [مطابقة مواد] → [توصية موردين موثوقين]
```

### 5.6 بوابة القوى العاملة — Workforce Portal (مستقلون/عاملون)

```
[لوحة القوى العاملة]
  ├── ملف المهارات (Skills Profile)
  │     [الملف] → [المهارات والرخص] → [معرض أعمال (صور/فيديو)] → [الشهادات]
  │     → [التوفر/المنطقة الجغرافية] → [سعر الخدمة/أجر اليومية]
  │
  ├── الوظائف (Jobs)
  │     [بحث وظائف] → [تفاصيل وظيفة] → [تقديم طلب] → {سيرة ذاتية + خطاب}
  │     → حالة التقديم: PENDING → SHORTLISTED → INTERVIEW → HIRED | REJECTED
  │
  ├── التدريب (Training)
  │     [سوق الدورات] → [دورة] → [تسجيل] → [إتمام دروس] → [شهادة] → [إضافتها للملف]
  │
  └── سجل العمل
        [مشاريع/مهام سابقة] → [تقييمات وردود] → [إحصائيات دخل]
```

### 5.7 بوابة مزوّد التدريب — Training Provider Portal

```
[لوحة مزوّد التدريب]
  ├── الدورات (Courses)
  │     [قائمة دوراتي] → [إنشاء دورة] → {محتوى: دروس فيديو/PDF/اختبارات}
  │     → [نشر] → حالة: DRAFT → PUBLISHED → ARCHIVED
  │
  ├── الطلاب والتسجيلات
  │     [التسجيلات] → [متابعة تقدم] → [إنهاء] → [إصدار شهادة]
  │
  └── الأداء
        [إحصائيات الاشتراكات] → [تقييمات الدورات] → [الإيرادات]
```

### 5.8 بوابة الإدارة — Admin Portal

```
[لوحة الإدارة]
  ├── النظرة العامة (Overview)
  │     [KPI: مستخدمون، مؤسسات، حجم تداول، طلبات تحقق معلقة، تذاكر دعم]
  │
  ├── التحقق (Verifications)
  │     [قائمة طلبات] → [تفاصيل وثائق] → {اعتماد / رفض} → [سجل تدقيق]
  │
  ├── المستخدمون والمؤسسات
  │     [بحث/تصفية] → [تفاصيل] → [إيقاف/تعطيل] → [تغيير حالة تحقق]
  │
  ├── المحتوى والوحدات
  │     [مراجعة منتجات/وظائف/دورات/مناقصات] → {نشر / إخفاء / إزالة}
  │
  ├── الدعم (CRM)
  │     [الفرص] → [العملاء المتوقعون] → [جهات الاتصال]
  │
  ├── التحليلات (Analytics)
  │     [تقارير النمو] → [تحليلات الأطراف الأربعة] → [تصدير]
  │
  └── الإعدادات
        [إدارة الأدوار والصلاحيات] → [سجل التدقيق Audit Log] → [إعدادات عامة]
```

## 6. تدفق الثقة والتحقق (Trust & Verification Flow)

نظام متدرج موحّد يعرضه الـ UI في كل نقطة قرار تجاري:

```
UNVERIFIED ── Trade License ──► BASIC ── VAT + وثائق أساسية ──► VERIFIED
     ▲                                                            │
     └── REJECTED/SUSPENDED ◄──── EXPIRED ◄──── بمرور الوقت      │
                                                                 ▼
                                        Certifications + Bank ──► TRUSTED
                                                                   │
                                            تدقيق دوري + ضمانات ──► FLAGSHIP
```

**قواعد العرض:**
- شارة المستوى تظهر في: بطاقة مورد، بطاقة منتج، نتائج البحث، مقارنة العروض.
- عند المستوى `UNVERIFIED` تُعرض CTA "أكمل التحقق" بدل إخفاء الملف.
- شارات المستويات ألوان ثابتة (معرّفة في Design System): رمادي → أزرق → أخضر → ذهبي → بنفسجي.

## 7. نموذج التنقل (Navigation Model)

| النوع | الاستخدام | مثال |
|---|---|---|
| **Navbar علوي عام** | متجر/وظائف/تدريب/مناقصات/مؤسسة/دخول | شريط ثابت فوق كل الصفحات العامة |
| **Sidebar بوابة الدور** | أقسام البوابة حسب الدور | لوحة المورد: الملف/المنتجات/المخزون/العروض/الطلبات/التحليلات |
| **Tabs داخل صفحة** | أقسام فرعية لنفس الكيان | صفحة المورد: نظرة عامة/منتجات/تقييمات/وثائق |
| **Stepper** | عمليات متعددة الخطوات | إنشاء RFQ، فحص جودة، إصدار شهادة |
| **Breadcrumbs** | عمق التنقل | السوق > مواد بناء > أسمنت > تفاصيل |
| **غلاف الصفحة (Page Shell)** | هيكل موحّد لكل بوابة | Header + Sidebar + Content + Actions |

**القاعدة:** عمق النقر ≤ 3 نقرات من لوحة البوابة إلى أي إجراء أساسي (تقديم عرض، إنشاء RFQ، رفع منتج).

## 8. مبادئ UX للغة والاتجاه (RTL/LTR)

### 8.0 دعم اللغات الثلاث — متطلب معتمد (v1.1)

| اللغة | الاتجاه | الحالة | الدور |
|---|---|---|---|
| **العربية** | RTL | واجهة أساسية | اللغة الافتراضية للمنصة |
| **الإنجليزية** | LTR | واجهة كاملة | اللغة الافتراضية الثانية |
| **الأردية** | RTL | واجهة كاملة | لغة معتمدة رسمياً (تُلبّي قطاعاً كبيراً من القوى العاملة وموردي المنطقة) |

قواعد أساسية لكل اللغات:

- **مبدّل اللغة (Language Switcher)** مكوّن نظامي واحد بـ 3 خيارات (العربية / English / اردو) في الـ Navbar وScreen Settings، مع بقاء لغة المستخدم محفوظة (cookie `NEXT_LOCALE`).
- **RTL يشمل العربية والأردية معاً** (لا RTL خاص بكل لغة على حدة) — البنية تُشتق من `dir` حسب مجموعة اللغة.
- **أطوال النصوص (Text Length):** لا يُعتمد تصميم يحمل نصوصاً عربية فقط. كل العناصر تُختبر بعينات نصوص طويلة وقصيرة في اللغات الثلاث (الأردية والإنجليزية غالباً أطول من العربية المختصرة). القواعد:
  - العناوين والأزرار تُقسّم `min-w-0` + `truncate`/`wrap` حسب السياق — لا ثبات بعرض نص واحد.
  - حقول النماذج تسمح بالتوسع الرأسي، ولا تُقتطع بيانات الإدخال.
  - جداول البيانات تُعتمد `min-w` لكل عمود + تفاف ذكي حسب الحاجة.
  - الأزرار: `whitespace-nowrap` فقط للنصوص القصيرة؛ للبقية التفاف تلقائي.
- **اختبار اللغات الثلاث إلزامي** لكل من: **Navigation** (الشريط، القوائم، الـ Sidebar، Breadcrumbs، Tabs، الـ Dropdowns) · **Forms** (التسميات، الـ placeholders، رسائل التحقق، الأخطاء) · **Tables** (الرؤوس، البيانات، الفرز، التصدير) — معيار قبول Sprint 1 (راجع §9 الوصولية و `docs/design-review/README.md`).

### 8.1 القواعد المشتركة

| المبدأ | التطبيق |
|---|---|
| **Logical Properties** | كل المسافات/الحدود/المحاذاة عبر `start/end` (ps-*، pe-*، ms-*، me-*) لا `left/right`. |
| **المرآة التلقائية** | أيقونات الاتجاه (أسهم، chevrons) تُقلب في LTR عبر `scale-x-[-1]` فقط للعناصر الاتجاهية — والسلوك نفسه سليم تلقائياً في الأردية (RTL). |
| **الرقام** | تقبل النظام أرقاماً هندية `٠١٢٣` وعربية غربية `0123`؛ يُعتمد تنسيق `Intl.NumberFormat` حسب اللغة (عربي/أردي/إنجليزي). |
| **القياس والوحدات** | وحدات القياس (كغم، م³، متر طولي) تبقى لاتينية/إنجليزية دائماً مهما كانت اللغة. |
| **الأسعار والعملة** | رمز العملة يظهر حسب اللغة المختارة (ر.س / SAR) مع ISO Code دائماً في الفواتير. |
| **التفاف النص** | العربية والأردية لا تستخدمان `letter-spacing`، وارتفاع السطر (line-height) أعلى من اللاتينية. |
| **اتجاه النماذج** | حقول النماذج تُقرأ من `start`، وأزرار الإجراء الأساسي في `end` (في العربية والأردية يمين، في الإنجليزية يسار). |
| **الاختصار اليدوي** | أي نص إنجليزي داخل واجهة عربية/أردية يُكتب `dir="ltr"` داخل حاوية `dir="rtl"`. |

### 8.2 الأردية — ملاحظات الطباعة (Urdu Typography Review)

| البند | القاعدة |
|---|---|
| **الخط (Script)** | الأردية تُكتب بـ **Nastaliq** (بخلاف العربية Naskh). الخط العربي النصي (Cairo/Plex Naskh) يقرأها وظيفياً لكن التميّز يتطلب خط Nastaliq مخصص. |
| **الخط المقترح** | **Noto Nastaliq Urdu** للعناوين/المحتوى مع fallback عربي Naskh، أو **Jameel Noori Nastaleeq** (وزن ثقيل للعرض). القرار النهائي في D9. |
| **ارتفاع السطر** | Nastaliq يتطلب `line-height` أعلى من Naskh (≥ 1.7) وتباعد أفقي أوسع — لا `letter-spacing` إطلاقاً. |
| **الاتجاه** | الأردية RTL كاملة — نفس البنية المعتمدة للعربية، بلا استثناءات. |
| **الأرقام** | الأردية تعتمد الأرقام الهندية الشرقية `۰۱۲۳` — يُدار عبر `Intl.NumberFormat('ur-PK')`. |
| **الترجمة الكاملة** | كل نص UI مترجم إلى UR (لا خلط عربي/أردي داخل واجهة أردية) — يقاس عبر معيار "دقة اللغة" في §11. |

## 9. إمكانية الوصول (Accessibility)

- تباين AA (4.5:1 للنص، 3:1 للعناصر الرسومية).
- تركيز مرئي واضح (`focus-visible` ring) عبر كل المكونات التفاعلية.
- تسلسل TAB منطقي يتبع اتجاه القراءة.
- النماذج: `label` مرتبطة بحقولها، رسائل خطأ `aria-describedby` وترتبط بالحقل.
- الجداول: `th scope`، و`caption` وصفية، وتخطيط بديل للجوال (بطاقات).
- لا تفاعل يعتمد على اللون وحده (أيقونات + نص + لون للـ Status).
- دعم `prefers-reduced-motion`.
