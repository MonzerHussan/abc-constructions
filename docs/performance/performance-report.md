## 3. مخاطر الأداء المحددة

### 3.1 N+1 queries
- خطر على قوائم RFQ/العروض/المنتجات عند تضمين علاقات متعددة.
- **التوصية:** استخدام `include` بشكل صريح، أو `findMany` مع select مضبوط؛ إضافة اختبار برمجي يفحص عدد الاستعلامات (يتطلب إعداد logging).

### 3.2 غياب الفهارس (Indexes)
- حقول مرشحة للفهرسة: `status`, `supplierId`, `productId`, `organizationId`, `createdAt`, `deadlineDate`.
- **التوصية:** إضافة فهارس مركبة على استعلامات القوائم الأكثر استخداماً (يُنفَّذ ضمن migration قادمة).

### 3.3 صور وملفات
- رفع الملفات يُخزن في `public/uploads` — النمو يحتاج CDN + ضغط الصور (Next Image يعمل مع `sharp`).
- **التوصية:** نقل الملفات إلى تخزين كائنات (S3/R2) عند التوسع.

### 3.4 تحميل JS
- صفحات `/admin` كبيرة وتستورد مكتبات (react-query, leaflet).
- **التوصية:** استخدم dynamic import/`next/dynamic` للخرائط (leaflet) والمكونات الثقيلة؛ التحقق عبر تقرير bundle.

## 4. خطة القياس والمراقبة

1. **قبل الإطلاق:** تشغيل Lighthouse محلياً على الصفحات الحرجة (`/`, `/auth/login`, `/procurement/rfqs`) وحفظ النتائج.
2. **أثناء Beta:** تشغيل `next build` مع تقرير sizes، وفحص Query log في مراقبة DB.
3. **بعد Beta:** إعداد RUM (Web Vitals) عبر Vercel Analytics أو أداة خارجية.
4. **اختبار تحميل:** إن لزم، تشغيل سيناريو k6 بسيط على مسار تسجيل الدخول وRFQ list.

## 5. الخلاصة

لا توجد عنق زجاجة معروف يمنع Beta على الحجم المتوقع للمستخدمين الأوائل، لكن يُنصح بأخذ قياسات baseline الآن (قبل الإطلاق) لتحديد مرجع يُقارن به لاحقاً، وبتنفيذ فهرسة الحقول الحرجة ومراجعة N+1 ضمن أول إصدارات ما بعد Beta.
