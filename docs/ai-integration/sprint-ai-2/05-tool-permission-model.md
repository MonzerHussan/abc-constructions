# Sprint AI-2 · Deliverable 5 — Tool Permission Model (نموذج أذونات الأدوات)

> **المسار:** AI & Integration Layer — Sprint AI-2
> **الحالة:** 📝 مواصفة — جاهزة للاعتماد
> **المرجع:** `08-ai-governance.md` §6 (مستويات القرار) · RBAC الحالي · `02-orchestrator-architecture.md` (التفويض)

---

## 1. الغرض

الوكلاء لا يملكون صلاحيات مباشرة — **أي إجراء (أداة)** يُنفَّذ عبر `ToolRegistry` يتحقق من: **هوية الوكيل + دور المستخدم + نوع الإجراء + تأثيره + موافقة**.

## 2. تصنيف الأدوات (Tool Classes)

| الفئة | مثال | مستوى القرار (08 §6) |
|-------|------|----------------------|
| **R (قراءة)** | قراءة بيانات عبر G1، استرجاع RAG | L1 — بدون موافقة |
| **N (إشعار)** | إرسال تذكير/إشعار للمستخدم | L1 |
| **D (مسودة)** | إنشاء مسودة (RFQ، عقد، رسالة) | L1 — يعرض للمراجعة |
| **W (كتابة منخفضة التأثير)** | تحديث تفضيلات/ذاكرة المستخدم | L2 — موافقة المستخدم الضمنية (قابلة للتراجع) |
| **A (كتابة عالية التأثير)** | إرسال عرض، اعتماد ترسية، شراء، تحويل مالي | **L3 — موافقة بشرية إلزامية** |

## 5.1 التصريح (Authorization Flow)

```
طلب أداة (agentId, action, ctx)
    → ToolRegistry.check(action)
        ├─ هل الأداة مكشوفة لهذا الوكيل؟ (tool-acl)
        ├─ هل دور المستخدم يسمح؟ (RBAC)
        ├─ هل المنظمة/المنظومة تسمح؟ (org scope)
        └─ مستوى التأثير (L1/L2/L3)
            ├─ L1 → تنفيذ مباشر
            ├─ L2 → تنفيذ + قابل للتراجع (سجل)
            └─ L3 → طلب موافقة بشرية ← موافقة/رفض
```

## 3. سجل الأدوات (Tool Registry)

```typescript
interface AgentTool {
  id: string;                 // "contractor.submit-rfq"
  action: string;             // إجراء قابل للتنفيذ
  impact: 'READ' | 'NOTIFY' | 'DRAFT' | 'LOW_WRITE' | 'HIGH_WRITE';
  agents: string[];           // الوكلاء المخولون (taxonomy)
  roles: string[];            // أدوار RBAC المسموحة
  scopes: ('user' | 'org' | 'ecosystem' | 'platform')[];
  requiresApproval: boolean;
  approvalRole?: string;      // من يوافق (مثال: المالك/المدير)
  auditLevel: 'none' | 'summary' | 'full';
}
```

## 4. مصفوفة أذونات أمثلة (Sample ACL)

| الأداة | الوكيل | التأثير | الموافقة |
|--------|--------|---------|----------|
| `contractor.read-boq` | Contractor, Procurement | READ | لا |
| `contractor.draft-rfq` | Contractor, Procurement | DRAFT | لا (مراجعة) |
| `contractor.submit-rfq` | Contractor | HIGH_WRITE | ✅ مالك المشروع |
| `supplier.draft-offer` | Supplier | DRAFT | لا (مراجعة) |
| `supplier.submit-offer` | Supplier | HIGH_WRITE | ✅ مدير المورد |
| `jobseeker.apply` | Job Seeker | HIGH_WRITE | ✅ المرشح نفسه |
| `recruiter.shortlist` | Recruiter | LOW_WRITE | لا |
| `finance.issue-invoice` | Finance (L3) | HIGH_WRITE | ✅ أمين مالي |
| `admin.toggle-feature` | Admin (L3) | HIGH_WRITE | ✅ مسؤول إطلاق |

## 5. قواعد الحوكمة (ربط 08)

1. **لا أداة Write لوكيل بدون تصنيف تأثير** — الافتراضي `READ`.
2. **HIGH_WRITE حصرية للموافقة البشرية** — لا وكيل يقرر لوحده.
3. **التراجع**: أدوات LOW_WRITE تُسجَّل وتدعم التراجع حيث أمكن.
4. **التدقيق الكامل** للأدوات المالية/القانونية/الأمنية (08 §8).
5. **رفض تلقائي** عند تجاوز حد الأدوات/الجلسة (منع طوفان الإجراءات).

## 6. التكامل مع RBAC الحالي

- أذونات الأدوات = **اقتران** (Role Permission) + **وكيل** + **منظومة** — لا استبدال.
- `roles[]` في الأداة تقرأ من نظام RBAC القائم — لا جدول أذونات ثانٍ (بلا تعديل Domain).

## 7. Human-in-the-Loop (آلية الموافقة)

| العنصر | القاعدة |
|--------|---------|
| من يوافق؟ | الدور المحدد في `approvalRole` (المالك/المدير/الأمين) |
| كيف؟ | عبر الواجهة القائمة (نفس نمط الموافقات) |
| مهلة | انتهاء مهلة = رفض افتراضي (أمان) |
| السجل | كل قرار موافقة/رفض يُسجَّل (08 §8) |
| الاستثناء | يمكن تفويض الموافقة صراحةً (لا تلقائياً) |
