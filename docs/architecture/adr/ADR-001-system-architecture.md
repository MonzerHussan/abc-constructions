# ADR-001: System Architecture — Modular Monolith with Service Layer

## التاريخ
2026-07-30

## الحالة
معتمد

## السياق
نحن نبني Construction Operating System (COS) يجب أن يستمر لمدة 10 سنوات مع إمكانية التوسع الأفقي والرأسي. في نفس الوقت، نحتاج إلى سرعة تطوير في المرحلة الحالية (MVP → Launch). الخيارات المعمارية المتاحة:

1. **Monolith كلاسيكي** — تطبيق واحد، كود واحد، قاعدة بيانات واحدة.
2. **Modular Monolith** — تطبيق واحد، لكن الكود مقسم إلى Modules معزولة، كل Module له Domain خاص به.
3. **Microservices** — خدمات منفصلة لكل Domain، كل خدمة لها قاعدة بياناتها ونشرها المستقل.

## الخيارات

| البعد | Monolith | Modular Monolith | Microservices |
|-------|----------|-----------------|---------------|
| سرعة التطوير حالياً | عالية جداً | عالية | منخفضة |
| عزل Domains | لا يوجد | موجود (برمجي) | كامل (شبكي) |
| تعقيد النشر | بسيط | بسيط | عالي جداً |
| تعقيد الفريق | بسيط | متوسط | عالي جداً |
| إعادة استخدام الـ Modules | لا يمكن | يمكن بسهولة | يمكن بصعوبة |
| اختبار التكامل | سهل | سهل | صعب |
| التكلفة التشغيلية | منخفضة | منخفضة | عالية |

## القرار
اخترنا **Modular Monolith with Service Layer** للأسباب التالية:
- **توازن بين السرعة والعزل:** يمكن للفريق التطوير بسرعة مع ضمان عدم تشابك الـ Domains
- **قابلية التوسع:** إذا احتجنا استخراج Domain كثيف الضغط إلى Microservice، Service Layer موجود مسبقاً
- **Event System:** يضمن عدم وجود اقتران مباشر بين الـ Domains حتى داخل التطبيق الواحد
- **لا Repository Pattern في البداية:** Service → Prisma مباشرة، Repository يُضاف فقط عند الحاجة الحقيقية (أكثر من DB، أكثر من ORM، أو Offline Storage)

## النتائج
- **إيجابي:** عزل Business Logic في Services، فصل مسؤوليات واضح، سرعة تطوير مقبولة
- **سلبي:** لا يزال تطبيقاً واحداً، إذا نما الفريق كثيراً قد يصبح التنسيق صعباً
- **محايد:** قاعدة بيانات واحدة حالياً (يمكن فصلها لاحقاً عند الحاجة)

## بدائل مستقبلية
- عندما يصبح Domain معين عالي الضغط (High Load): استخراجه إلى Microservice منفصل
- عندما يصبح الفريق أكبر من 3 فرق: التفكير في Microservices
- Service Layer الحالي جاهز لدعم هذا الانتقال
